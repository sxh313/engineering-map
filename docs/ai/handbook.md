## 01 · Agent 最小闭环 {#stage-01}

### 核心结论

大模型本身只负责根据输入生成下一段内容。Agent 在模型外增加了一个控制循环：把目标交给模型，解析模型决定，执行工具，把执行结果重新放回上下文，再判断是否继续。

最小闭环可以写成下面的伪代码：

```text
messages = [system, user_goal]

repeat until stopped:
  decision = model(messages, tools)
  if decision is final_answer:
    return decision
  result = execute(decision.tool, decision.arguments)
  messages.append(decision)
  messages.append(result)
```

### 必须理解的边界

- **聊天**：控制权主要在人，用户决定下一轮问什么。
- **Workflow**：控制权主要在预先写好的程序，步骤通常是确定的。
- **Agent**：程序提供边界，模型在边界内动态选择下一步动作。
- **工具结果不是最终答案**：它是 Observation，需要回到模型或确定性逻辑继续判断。
- **停止条件必须外置**：最大轮数、超时、预算、成功判定和人工接管不能只靠模型自觉。

### 一次完整循环怎样运行

```text
用户目标
  ↓
Context Builder 组装规则、状态和证据
  ↓
模型输出 Final Answer 或 Tool Call
  ↓                         ↘
Tool Executor 校验并执行      满足验收条件 → 结束
  ↓
Observation 写回轨迹 → 进入下一轮
```

工程实现中，模型只负责提出“候选动作”。工具注册表确认工具是否存在，Schema 校验参数是否合法，权限层判断是否允许执行，执行器负责超时和错误分类，验收器判断任务是否真的完成。这样才能把模型的不确定性限制在受控边界内。

### 最容易失败的地方

| 失败 | 表现 | 处理方式 |
| --- | --- | --- |
| 轨迹断裂 | Tool Call 和 Tool Result 对不上 | 为每次调用保存稳定的 call ID |
| 无限循环 | 重复调用同一工具却没有新信息 | 设置轮数、预算与重复动作检测 |
| 提前结束 | 模型声称成功，真实状态没有变化 | 用确定性验收器检查结果 |
| 错误不可见 | 工具只返回“失败” | 返回类型、原因、是否可重试和建议动作 |

### 面试时怎么讲

先用一句话定义 Agent，再画出 Model–Action–Observation 循环，最后补充停止条件、权限、可观测性和验收。不要只说“Agent 会自主调用工具”，要说明自主决策发生在哪一层，程序又怎样限制它。

**完成标准：** 能手写最小循环；能解释消息顺序；能注入一次工具失败并观察恢复；能证明系统不会无限执行。

### 自测

1. 为什么“模型会 Tool Calling”仍不等于系统已经是可靠 Agent？
2. 工具报错后，应该把什么信息放回上下文？
3. 最终成功应由模型声明，还是由程序验证？

<details class="study-answer"><summary>展开自测提示</summary>

Tool Calling 只是生成结构化调用意图；可靠系统还需要参数校验、权限、错误分类、循环控制和验收。报错应返回错误类型、可重试性、已产生的副作用和下一步可用信息。最终成功由程序或外部验证器判断，模型可以提供解释但不能单独作为证据。

</details>

## 02 · 上下文工程 {#stage-02}

### 核心结论

上下文不是聊天记录的简单拼接，而是一次推理前的“信息装配结果”。装得太少会遗漏约束，装得太多会引入噪声、提高成本并稀释重点。

一个实用的装配顺序是：

```text
系统规则 → 当前目标 → 必要状态 → 相关记忆或检索证据 → 最近轨迹 → 本轮输入
```

### 四种常见策略

- **裁剪**：删除确认无关的信息，适合工具输出过长的场景。
- **摘要**：压缩历史语义，但必须保留不可丢失的约束、决定和待办。
- **按需加载**：先放索引，需要时再取正文，适合大型代码库和知识库。
- **缓存**：复用稳定前缀，减少重复计算；缓存命中不代表内容仍然正确。

上下文、运行状态和长期记忆要分开：运行状态服务于任务恢复，长期记忆服务于跨会话偏好，上下文只是本轮真正交给模型的内容。

### 上下文是怎样组装的

```text
不可覆盖的系统规则
  + 当前任务与验收条件
  + 结构化运行状态
  + 按需检索的知识与记忆
  + 最近必要的动作轨迹
  + 当前用户输入
  = 本轮 Model Context
```

一个实用的 Context Builder 应明确每类信息的来源、优先级、Token 预算和淘汰策略。稳定规则放在前缀，任务状态用结构化字段保存，历史轨迹只保留影响下一步的部分，长文档先给索引再按需读取。

### 压缩时不能丢什么

- 用户目标、不可违反的约束和验收条件。
- 已经产生副作用的工具动作及其结果。
- 当前计划、未完成项和失败原因。
- 文件路径、资源 ID、版本号等继续任务所需的引用。

摘要适合压缩解释性对话，不适合替代真实状态。上下文变短以后，应使用固定回归任务检查约束是否仍被遵守、工具选择是否变化、恢复是否仍然正确。

### 面试时怎么讲

用“选择什么进入模型”解释 Context Engineering，然后把 Context、State、Transcript、Memory 四者分开。补充一个实际取舍：例如面对十万行日志，先由程序提取错误窗口和统计信息，只有需要时才继续读取原文。

**完成标准：** 为同一任务设计三种上下文方案，记录 Token、成功率和关键错误，能用实验解释为什么选择其中一种。

### 自测

1. 为什么更长的上下文不一定得到更好的回答？
2. 哪些信息绝不能只保留在摘要里？
3. 工具返回十万行日志时，你会怎样决定给模型看什么？

<details class="study-answer"><summary>展开自测提示</summary>

更长会增加噪声、位置偏差、成本和冲突。不可丢失的规则、验收条件、资源 ID、已产生副作用的动作和待办应保留结构化原值。长日志先用确定性程序提取错误窗口、统计和关键时间点，模型需要时再读取原文片段。

</details>

## 03 · Memory 与 RAG {#stage-03}

### 核心结论

Memory 解决“系统应该记住什么”，RAG 解决“回答当前问题需要查到什么”。它们都向上下文提供信息，但生命周期和可靠性要求不同。

### RAG 的基本链路

1. 文档切分并保留来源位置。
2. 将问题转换成检索查询。
3. 召回候选片段。
4. 通过过滤或重排找到真正相关的证据。
5. 让模型只基于证据回答，并给出引用。
6. 当证据不足时拒答或请求补充信息。

错误需要分层判断：没找到正确内容是召回问题，找到了却排在后面是重排问题，证据正确但答案错误是生成问题。只看最终答案，很难知道应该修哪一层。

### Memory 的三种常见类型

- **会话轨迹**：当前任务发生过什么。
- **用户记忆**：相对稳定的偏好、身份和约束。
- **知识记忆**：可引用、可更新的外部事实。

三者不应混成同一张“万能表”，否则很难处理过期、权限和删除要求。

### 从文档到可引用答案

```text
文档解析 → 结构化切分 → 建索引 → 查询改写
→ 混合召回 → 过滤 / 重排 → 证据打包 → 带引用生成
```

切分时要保留标题层级、页码、表格归属和来源版本。召回阶段可以组合关键词与向量检索，重排阶段解决“找到了但位置靠后”的问题，生成阶段只消费经过筛选的证据。没有足够证据时，系统应明确说明缺口。

### Memory 的写入也需要门禁

长期记忆不应自动保存每句对话。写入前至少判断：信息是否稳定、未来是否有用、用户是否同意、是否包含敏感数据、何时过期、如何修改或删除。读取时还要按用户、组织和任务权限过滤。

### 诊断顺序

| 现象 | 优先检查 |
| --- | --- |
| 完全没找到答案 | 解析、切分、查询、召回 |
| 找到了但排名靠后 | 重排与过滤 |
| 证据正确但回答错误 | Prompt、上下文和生成约束 |
| 引用位置不对 | Chunk 元数据和答案对齐 |

**完成标准：** 实现一个带来源引用的检索问答；准备无答案问题；分别留下召回失败、重排失败和生成失败样例。

### 自测

1. 用户说“以后都用中文回答”应进入哪种记忆？
2. 检索正确但回答错误时，为什么不该先调整向量模型？
3. 引用能证明哪些事情，又不能证明哪些事情？

<details class="study-answer"><summary>展开自测提示</summary>

语言偏好属于用户长期记忆，并应允许查看和删除。检索已经正确时，问题更可能在证据打包、提示或生成约束。引用证明答案有对应来源，不能自动证明来源真实、最新，也不能证明模型的推导必然正确。

</details>

## 04 · Tool、MCP 与 Skills {#stage-04}

### 核心结论

Tool 是系统可以执行的动作，MCP 是连接工具与数据源的一种标准协议，Skill 是可复用的任务方法和约束。三者解决的问题不同，不能互相替代。

一个可靠工具至少需要：

- 明确的名称与用途，避免模型误选。
- 可校验的参数 Schema，非法输入在执行前被拒绝。
- 超时、取消和资源限制。
- 可区分的错误类型，例如参数错误、权限拒绝、业务失败和系统故障。
- 对写入操作提供预览、确认、审计和幂等保护。

### 风险分级

- **只读动作**：通常可以自动执行，但仍要限制读取范围。
- **可恢复写入**：先展示变更，再让用户确认。
- **难恢复动作**：删除、付款、发布等需要更严格的身份与权限检查。

模型给出的工具参数只能视为候选输入，不能直接当作可信命令。真正的安全边界必须由确定性程序实现。

### Tool、MCP、Skill 怎样协作

| 层次 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Tool | 一个可执行动作及输入输出契约 | 完整任务方法 |
| MCP | 工具、资源和 Prompt 的标准连接方式 | 自动保证工具安全 |
| Skill | 完成一类任务的步骤、判断与约束 | 代替宿主权限检查 |
| Runtime | 调度、权限、重试、状态和审计 | 决定业务答案内容 |

工具设计优先窄而清晰：读取和写入分开，高风险动作单独建工具，返回结构化结果。工具数量很多时，先按任务检索候选工具，再把少量定义交给模型，避免一次注入全部 Schema。

### 一次安全调用的控制点

```text
模型候选参数 → Schema 校验 → 权限检查 → 用户确认（需要时）
→ 幂等键 → 执行 / 超时 → 结构化结果 → 审计日志
```

### 面试时怎么讲

不要停在“MCP 是 USB-C”。应说明 MCP 统一了连接和发现，但身份、授权、数据范围、提示注入、供应链审计和副作用控制仍由宿主系统负责。

**完成标准：** 实现一个只读工具和一个写入工具；覆盖参数错误、权限拒绝、超时、重复提交和成功五类轨迹。

### 自测

1. 为什么 Schema 既是提示信息，也是运行时边界？
2. MCP 解决了互操作后，哪些安全问题仍然存在？
3. 怎样避免任务重试时重复创建同一资源？

<details class="study-answer"><summary>展开自测提示</summary>

Schema 帮模型形成参数，同时由执行器拒绝非法输入。MCP 不自动解决身份、授权、数据范围、提示注入、恶意服务和副作用控制。写入动作使用业务唯一键或幂等键，并在重试前查询真实状态。

</details>

## 05 · Agent Runtime {#stage-05}

### 核心结论

Runtime 管理的是一个任务从开始到结束的生命周期：状态、检查点、并发、重试、取消、恢复和资源边界。它是 Agent 从演示程序走向可用系统的关键层。

### 需要分开的三种数据

- **Transcript**：完整发生记录，用于审计和回放。
- **Runtime State**：程序恢复任务所需的结构化状态。
- **Model Context**：本轮精选后真正发给模型的信息。

每个工具动作最好经历“计划 → 执行中 → 已完成或失败”的状态变化。检查点要记录动作是否已经产生副作用，恢复时才能决定继续、跳过还是补偿。

### 可靠恢复原则

- 写入操作使用幂等键或唯一业务标识。
- 重试只针对可重试错误，并设置退避和上限。
- 取消信号要能传到正在运行的工具。
- 恢复前先读取真实外部状态，不能只相信旧日志。

### Runtime 的状态机

```text
pending → running → waiting_tool / waiting_human
   ↑           ↓              ↓
retrying ← failed         resumed
               ↘           ↙
               completed / cancelled
```

每次状态转换都应记录任务 ID、步骤 ID、输入摘要、版本、时间和副作用标记。长任务用检查点保存可恢复状态；等待用户确认时释放执行资源；恢复后先核对外部世界，再决定重试、跳过或补偿。

### 三类失败要分开

- **瞬时故障**：网络抖动、限流，可以退避重试。
- **确定性错误**：参数非法、资源不存在，修改输入后再执行。
- **业务冲突**：资源已变更、权限不足，需要重新规划或交给人处理。

“所有错误重试三次”会重复副作用并浪费预算。重试策略必须基于错误类型和动作幂等性。

### 面试时怎么讲

用“工具成功但检查点没写入”的双写问题展示深度：恢复时查询真实外部状态，借助幂等键确认动作是否已完成，再更新本地状态。

**完成标准：** 任务可以暂停、取消和恢复；进程中断后不会重复写入；Trace 能说明每次重试的原因。

### 自测

1. 为什么把所有聊天消息保存下来仍不等于支持恢复？
2. 工具刚成功、系统却在写检查点前崩溃，恢复时怎么办？
3. 什么错误适合重试，什么错误必须立即停止？

<details class="study-answer"><summary>展开自测提示</summary>

聊天记录缺少结构化状态、步骤阶段和副作用标记。恢复时应使用幂等键查询外部系统，确认动作是否已发生。网络抖动、限流等瞬时错误可退避重试；非法参数、权限拒绝和业务冲突要修正、重新规划或交给人处理。

</details>

## 06 · Coding Agent 与交互 {#stage-06}

### 核心结论

Coding Agent 不只是生成代码。它需要观察文件、搜索调用关系、提出补丁、运行验证，并在可能造成损失的动作前让人做决定。

### 一次安全修改的流程

1. 读取仓库规则和目标文件。
2. 搜索相关调用链，确认影响范围。
3. 生成最小补丁，不覆盖无关改动。
4. 展示 Diff 或变更摘要。
5. 在权限允许时应用补丁。
6. 执行测试、构建或静态检查。
7. 报告已验证内容和仍然未知的风险。

Computer Use 和浏览器 Agent 也遵循相同原则：先观察，再定位，再行动，行动后重新读取界面确认真实结果。屏幕看起来“像成功”不等于后台状态已经成功。

### Coding Agent 的观察—修改—验证闭环

```text
读取规则 → 搜索符号与调用链 → 建立修改假设 → 生成最小 Diff
→ 执行验证 → 读取失败证据 → 修正 → 汇报结果与边界
```

文件搜索、补丁应用、终端执行和浏览器操作应是分开的工具。修改前保存基线，修改后展示 Diff，验证命令和输出要与具体版本关联。并行任务需要独立工作区，避免两个 Agent 同时覆盖同一文件。

### 人应在哪些位置介入

读取公开代码通常可以自动进行；修改本地文件应保留 Diff；推送、发布和写入外部系统要根据影响确认；删除、付款、权限变更等动作必须由不可绕过的规则保护。人工介入点应由动作风险决定，而不是由模型“感觉是否危险”决定。

### 面试时怎么讲

准备一个真实修改案例，按“搜索到的证据—选择的最小改动—执行的验证—发现的限制”讲。重点展示你怎样缩小影响范围和证明结果。

**完成标准：** 让 Agent 完成一次跨文件修改；保存搜索证据和 Diff；故意制造一次验证失败并完成修复；能回滚到修改前状态。

### 自测

1. 为什么整文件重写比最小补丁风险更高？
2. 人工确认应该放在哪些动作前？
3. Agent 自己说“测试通过”为什么不算验证证据？

<details class="study-answer"><summary>展开自测提示</summary>

整文件重写更容易覆盖无关改动并扩大审查范围。确认点依据副作用和可恢复性设置，例如发布、外部写入、权限变化和删除。验证证据应包含实际命令、输出、版本和结果，模型的陈述只是未经验证的结论。

</details>

## 07 · 评估与可观测性 {#stage-07}

### 核心结论

Trace 解释一次任务发生了什么，Eval 判断系统在一组任务上表现如何。没有 Trace 很难定位失败，没有 Eval 很难证明改动整体变好。

### 建议记录的运行数据

- 输入、期望结果与评分规则。
- 模型、提示、工具和代码版本。
- 每一步决策、参数、Observation 和耗时。
- Token、成本、重试次数与最终状态。
- 确定性检查、人工评分或规则评分。

评估集应同时包含正常任务、边界条件和已知失败。报告不能只给平均分，还要展示改善样例、退化样例和没有变化的样例。

### 指标的三层结构

- **结果层**：任务是否完成，输出是否正确。
- **过程层**：工具选择、参数、步骤数和恢复行为是否合理。
- **系统层**：延迟、成本、可用性和安全事件。

### 从 Trace 到 Eval

单条 Trace 用于回答“这次为什么失败”，评估集用于回答“这个版本整体是否更好”。每条评估样例至少包含输入、期望、允许的路径、禁止行为和评分方法。确定性任务优先使用代码验证器；开放任务再组合规则、人工和模型评分。

```text
线上失败 → 去敏 → 归类 → 加入回归集
                         ↓
候选改动 → 离线运行 → 分组比较 → 发布或回滚
```

### 报告怎样避免平均数陷阱

除了整体成功率，还要按任务类型、难度、工具、失败原因和风险等级分组。一次改动可能让简单任务平均分上涨，却让高风险任务出现严重退化。报告中至少展示一个改善案例和一个退化案例。

### 面试时怎么讲

先说任务成功率，再说过程指标和系统指标；说明你的验证器怎样工作、哪些情况需要人工判断、评估集怎样防止数据泄漏。

**完成标准：** 建立至少 15 条小型评估集；保存版本和 Trace；生成分组结果；对一个退化样例完成原因定位。

### 自测

1. 为什么只使用“模型评分模型”风险很高？
2. 平均分上涨时，系统仍可能出现什么退化？
3. 一条 Trace 至少要能追溯到哪些版本信息？

<details class="study-answer"><summary>展开自测提示</summary>

模型评分可能有偏好、提示敏感性和自我偏袒。平均分可能掩盖高风险任务、少数群体或长任务退化。Trace 至少关联模型、Prompt、工具、代码、数据集和配置版本。

</details>

## 08 · 训练与行为优化 {#stage-08}

### 核心结论

看到失败时，先定位失败来自上下文、工具、编排、数据还是模型能力。只有稳定复现且无法通过系统设计解决的问题，才值得考虑训练。

### 三类方案

- **系统改进**：修改提示、上下文、工具或流程，成本最低且容易回滚。
- **SFT**：让模型更稳定地模仿目标回答或操作格式，依赖高质量示例。
- **偏好优化或 RL**：根据比较或奖励信号调整行为，要求可靠评价信号和更高工程成本。

训练前必须先有独立评估集、数据来源记录和停止条件。否则训练后只会看到“感觉变好”，无法知道是否损害了其他能力。

### 先判断问题发生在哪一层

| 失败来源 | 优先动作 |
| --- | --- |
| 缺少事实 | 改检索和上下文 |
| 工具不会用 | 改描述、Schema、示例和反馈 |
| 流程容易跑偏 | 改 Runtime 和验收器 |
| 输出格式不稳定 | Prompt、约束解码或 SFT |
| 多步策略长期不佳 | 在可靠奖励下考虑偏好优化或 RL |

训练数据要保留目标、轨迹、工具调用、Observation 和最终结果之间的因果关系。只收集漂亮答案会让模型学不到何时调用工具以及失败后如何恢复。训练集、验证集和真实评估集应按任务来源隔离。

### 从训练到部署

```text
失败定义 → 数据构造与清洗 → 基线评估 → 训练
→ 离线回归 → 推理服务验证 → 小流量发布 → 监控 / 回滚
```

训练收益还要扣除推理成本、延迟、模型维护和数据治理成本。有时小模型经过高质量系统设计已经够用，无需追求更复杂的训练方案。

**完成标准：** 为一个稳定失败写出“不训练 / SFT / RL”三种方案，给出选择依据；能解释数据格式、Loss Mask、评估与发布门禁。

### 自测

1. 工具参数经常缺字段，应该先训练还是先加强 Schema 与重试提示？
2. SFT 数据为什么不能直接来自未经清洗的线上日志？
3. 训练指标改善后，为什么仍要检查真实任务成功率？

<details class="study-answer"><summary>展开自测提示</summary>

先改 Schema、示例和错误反馈，因为更便宜、可解释、易回滚。线上日志可能包含敏感信息、错误轨迹、低质量答案和分布偏差。训练损失只说明对训练目标的拟合情况，不能代替真实任务、工具轨迹和安全回归评估。

</details>

## 09 · 持续进化 {#stage-09}

### 核心结论

持续进化不是让 Agent 随意修改自己，而是把真实失败转化成受控候选改进，再经过离线验证、人工审核和灰度发布。

### 安全改进闭环

```text
失败收集 → 去敏与分类 → 原因定位 → 生成候选方案
→ 离线评估 → 人工审核 → 灰度发布 → 监控 → 保留或回滚
```

知识、提示、程序和模型参数是四种不同更新面。知识更新通常最容易回滚，程序和权限边界的更新风险更高，模型参数更新影响最广。不同更新面需要不同审批和验证强度。

### 必须设置的门禁

- 候选改进不能绕过已有测试和权限检查。
- 线上轨迹进入数据集前要去除敏感信息。
- 同时监控质量指标和安全回归指标。
- 每次发布都保留版本、证据和回滚方法。

### 哪些东西可以进化

| 更新面 | 示例 | 风险与验证 |
| --- | --- | --- |
| Knowledge | 补充文档、修正事实 | 检查来源、时效和权限 |
| Prompt / Skill | 改步骤、规则、示例 | 用回归集检查行为变化 |
| Tool / Code | 新增工具、修复 Runtime | 代码审查、测试、沙箱与灰度 |
| Model | SFT、偏好优化、RL | 独立评估、能力回归和安全门禁 |

系统不应让生产 Agent 直接改写自己的核心权限或部署逻辑。Agent 可以提出候选补丁、生成新测试和解释失败，人和自动化门禁负责验证与发布。

### 经验怎样回流

```text
真实轨迹 → 去敏与质量筛选 → 失败聚类 → 候选经验
→ 离线重放 → 与基线比较 → 审核 → 灰度 → 持续监控
```

### 面试时怎么讲

把“自我进化”落到版本化工程：谁提出改动、谁验证、用什么数据、如何限制权限、怎样回滚。这样比抽象谈 Reflection 更可信。

**完成标准：** 从三条失败轨迹形成一个候选改进；补充回归样例；比较改动前后结果；保留拒绝发布和回滚路径。

### 自测

1. 为什么线上失败不能直接自动进入训练集？
2. 更新知识库和更新模型参数的风险有什么不同？
3. 自动生成补丁后，发布前至少要经过哪些门禁？

<details class="study-answer"><summary>展开自测提示</summary>

失败轨迹可能含隐私、攻击内容、错误标签和偶发噪声。知识更新范围更局部且容易撤回，参数更新影响面更广、原因更难定位。补丁至少要经过去敏、代码审查、自动检查、离线评估、权限审计和可回滚发布流程。

</details>

## 10 · 多 Agent 与生产项目 {#stage-10}

### 核心结论

多 Agent 的价值来自并行、权限隔离、上下文隔离或专业角色，而不是角色数量。能用一个 Agent 加确定性函数完成的任务，不必为了形式拆成多个 Agent。

### 拆分前先问四个问题

1. 子任务之间是否真的可以并行？
2. 不同角色是否需要不同权限或工具？
3. 单个上下文是否已经过长或相互干扰？
4. 协调成本是否低于拆分带来的收益？

### 协作协议需要明确

- 每个角色接收什么输入、产出什么结果。
- 共享哪些事实，隔离哪些私有上下文。
- 冲突由谁裁决，失败由谁恢复。
- 总预算、最大并发和停止条件是什么。

生产项目应先建立单 Agent 基线，再引入多 Agent，并比较质量、延迟、成本和维护复杂度。没有对照数据，就无法证明拆分值得。

### 一种可控的生产结构

```text
                    ┌→ 检索 Agent ─┐
用户 → Orchestrator ┼→ 执行 Agent ─┼→ Validator → 最终结果
                    └→ 审查 Agent ─┘
                         ↓
                 共享任务状态 / 独立上下文
```

Orchestrator 负责拆分、预算和汇总，专业 Agent 只接收完成子任务所需的上下文，Validator 使用独立规则验收。共享状态应结构化，角色之间通过明确消息协议通信，不把所有聊天记录广播给所有成员。

### 多 Agent 的真实成本

- 更多模型调用带来延迟和费用。
- 多份上下文容易产生事实不一致。
- 并行写入会引入资源冲突。
- 错误会跨角色传播，调试链路更长。
- 权限扩大后，安全审计更复杂。

### 从知识到完整作品

以面试诊断 Agent 为例：Web 接收简历和目标岗位，Query Engine 统一模型，Knowledge 提供带引用的岗位与项目证据，Runtime 管理长任务和恢复，Evaluator 检查问题覆盖、证据引用和建议质量。先完成单 Agent 版本，再把检索或评分拆成独立角色并做对照实验。

### 面试时怎么讲

先解释为什么拆分，再给出通信协议、状态归属、失败恢复和对照指标。不要用“每个角色更专业”作为唯一理由。

**完成标准：** 有单 Agent 基线；至少一个子任务可独立验收；记录质量、成本和延迟对比；能处理子 Agent 超时与部分失败。

### 自测

1. “规划 Agent + 执行 Agent”一定比单 Agent 好吗？
2. 多个 Agent 共享全部上下文会带来什么问题？
3. 怎样证明多 Agent 架构的收益超过协调成本？

<details class="study-answer"><summary>展开自测提示</summary>

只有拆分带来的并行、隔离或专业收益超过通信成本时才值得。共享全部上下文会增加成本、污染角色边界并传播错误。用同一评估集比较单 Agent 与多 Agent 的成功率、延迟、成本、恢复率和维护复杂度。

</details>

## 附录 A · 框架与 SDK 选型 {#appendix-frameworks}

框架不能代替架构判断。选型时先回答六个问题：状态是否显式、流程是否需要图结构、工具是否很多、是否要恢复、是否需要多 Agent、最终运行在哪个宿主。

| 类型 | 代表方案 | 适合场景 | 主要代价 |
| --- | --- | --- | --- |
| 原厂 SDK | OpenAI Agents SDK、Google genai、Anthropic SDK | 希望紧跟模型原生能力 | 跨厂商迁移需要适配 |
| 图编排 | LangGraph | 分支、并行、循环和状态恢复较复杂 | 状态设计与调试成本更高 |
| 通用应用框架 | LangChain、Semantic Kernel、Mastra | 需要现成组件与生态集成 | 抽象层可能掩盖真实调用链 |
| 多 Agent 框架 | AgentScope、AutoGen、AgentUniverse | 角色协作、分布式或企业治理 | 协调、成本和错误传播更复杂 |
| 研究型工作流 | DeerFlow | Deep Research、多阶段报告生成 | 对特定工作流依赖较强 |
| 全栈 UI 框架 | Vercel AI SDK | Web 流式交互、React/Next.js 应用 | 不负责完整后端 Runtime |
| Go 生态 | Eino | Go 服务、流式处理和高并发 | 社区资源少于 Python/TS |
| 最小 Harness | 自写 Loop、GitAgent 模式 | 学习原理或需要完全掌控边界 | 可靠性能力都要自己实现 |

### LangGraph 的统一理解

LangGraph 的核心不是“画图”，而是把状态、节点和边变成一等公民：

- **State** 保存节点之间共享的数据，更新时尽量返回增量。
- **Node** 承担一个可验证步骤，输入状态并返回状态变化。
- **Edge** 表示确定顺序，Conditional Edge 表示动态路由。
- **Fan-out / Fan-in** 用于并行分析与结果聚合。
- **Checkpoint** 让长流程支持暂停、恢复和人工介入。

如果流程只是一次模型调用或三个固定步骤，用普通函数会更清楚。只有当状态转移本身成为主要复杂度时，图框架才真正有价值。

### 三大 SDK 的共同协议

虽然接口名称不同，三者最终都在做同一件事：描述工具 → 发送消息 → 接收工具请求 → 本地执行 → 回传结果 → 继续生成。选型时比较自动循环、流式事件、模型覆盖、多模态、Handoff、Tracing 和部署环境，而不是只比较示例代码行数。

## 附录 B · Coding Agent 与 Harness 对比 {#appendix-harnesses}

五类系统可以放到同一张能力地图中理解：

| 系统 | 最值得学习的部分 | 适合借鉴的设计 |
| --- | --- | --- |
| Claude Code 渐进课程 | 从 Loop 逐步加入 Tools、Todo、Subagent、Skill、Compact、Teams | 用小步演进理解复杂系统 |
| Codex CLI | 配置层级、审批策略、平台沙箱、MCP 与线程式 SDK | 把权限和隔离放在模型之外 |
| Pi | Provider 适配、Extension、Package、树形 Session 与恢复 | Runtime、Transcript、Context 分层 |
| DeepSeek Harness | 插件内核、LLM 接缝、Session Log、Inbox、Runtime Surface | 将大部分能力设计成可替换接缝 |
| OpenClaw | 从最小 Loop 推导 RAG、工具、记忆、多 Agent 和部署 | 先理解机制，再引入框架 |

### 渐进构建顺序

1. **Loop**：完成 Model–Tool–Observation 闭环。
2. **Tool Registry**：用注册表替代硬编码分支。
3. **Todo / Plan State**：让计划成为可观察状态。
4. **Session Log**：记录不可变事件，作为事实源。
5. **Context Builder**：从事实源挑选本轮上下文。
6. **Compaction**：压缩历史但保留任务状态和关键决定。
7. **Subagent**：用独立上下文处理明确子任务。
8. **Background Task**：非阻塞运行长工具，并支持状态查询和取消。
9. **Team Protocol**：定义消息、责任、冲突和完成条件。
10. **Workspace Isolation**：并行修改时隔离文件和 Git 状态。

### Harness 的五条工程判断

- Loop 是控制平面，不应同时承担所有业务实现。
- 工具“存在”不代表模型“有权限执行”。
- Session Log 记录事实，Context 是从事实中构造的工作集。
- 用户插话、取消和审批都是独立事件，不能伪装成普通聊天消息。
- 插件可以扩展能力，但安全边界必须由不可绕过的宿主机制保证。

## 附录 C · 七个应用实战 {#appendix-practice}

### 1. 用 Agent 发布个人主页

从需求澄清、信息架构、视觉实现、构建检查到 GitHub Pages 部署。重点不是“一句话生成网页”，而是如何保存设计决定、检查移动端、处理资源路径并验证线上状态。

### 2. AI Coding 面试

把题目拆成输入输出、约束、例子、算法选择、边界测试和复杂度说明。Agent 可以辅助搜索和验证，但候选人必须能解释关键决定，并区分“代码能跑”和“答案可交付”。

### 3. 日常开发工作流

为仓库准备规则、常用命令和验证入口；先搜索再修改，先最小补丁再扩展，使用测试和 Diff 作为证据。长任务通过计划、检查点和阶段摘要控制上下文。

### 4. Auto Harness

从失败轨迹中识别重复工具调用、状态丢失、错误分类不清和提前结束，再修改运行骨架。每个改动都必须有失败样例和回归验证，不能只优化成功 Demo。

### 5. Eval-Driven Practice

先建立 15–30 条小型评估集，再改提示、工具或模型。记录版本、Trace、耗时、成本和评分，报告同时展示改善与退化。

### 6. RSI 求解优化

把一次求解失败转化成策略候选，通过离线问题集比较新旧策略。真正的 RSI 需要受控候选、外部验证和回滚，而不是让模型未经审核修改自身生产逻辑。

### 7. 云端 Bot Agent

关注渠道接入、身份、会话、异步事件、限流、重试、长任务状态与用户通知。不同聊天渠道只是入口，核心 Runtime 应保持一致。

每个实战统一留下五类证据：需求说明、可运行代码、一次失败轨迹、评估结果和部署说明。

## 附录 E · 十二步生产项目 {#appendix-project}

以“面试诊断 Agent”为示例，可以用下面十二步把知识串成一个完整作品：

1. **PRD**：明确用户、输入、输出、成功标准、隐私和非目标。
2. **系统架构**：划分 Web、API、Query Engine、Tools、Knowledge、Runtime 和 Storage。
3. **Query Engine**：统一多 Provider，处理流式响应、超时、重试、缓存和路由。
4. **Tools & Skills**：原子工具负责动作，Skill 负责可复用任务方法。
5. **知识库**：支持关键词与向量双路检索，答案必须带来源证据。
6. **Context & Memory**：分离当前任务状态、短期历史、长期偏好和知识证据。
7. **Permission & Session**：权限分级、确认、检查点、恢复和审计日志。
8. **Hook & Command**：用确定性钩子治理输入、工具前后、输出和错误流程。
9. **Sub-agent**：将检索、评分或总结包装为边界清晰的子任务。
10. **STT 与语音**：转写、说话人分离、时间戳和口语表现分析。
11. **部署与演示**：环境配置、可复现启动、正常用例和可恢复失败用例。
12. **Web UI**：上传、进度、流式结果、证据查看、失败恢复与移动端体验。

### 推荐架构

```text
Web / CLI
   ↓
API + Session
   ↓
Runtime / Query Engine
   ├── Model Provider
   ├── Tools & Skills
   ├── Knowledge Retrieval
   ├── Memory & Context
   └── Eval / Trace / Audit
```

项目展示时至少演示一次正常分析、一次工具失败后的恢复，以及一份可以追溯到版本的评估结果。
